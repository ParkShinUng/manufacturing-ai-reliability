# Codex challenge - ADR-0022 (JSON Schema validation in .NET)

> Raw output, transcribed verbatim from the `codex exec` run of 2026-09-29. Read-only, with fact
> checking against nuget.org and upstream issue trackers. Verdict: **REJECT** - it rejected the
> hand-rolled-validator recommendation and named an option the ADR had missed (Corvus).

F1 - P1 - `docs/07-adr/ADR-0022-json-schema-validation-in-dotnet.md:57` - Option C understates the validator surface. The current schemas use more than the listed/simple subset: `exclusiveMinimum`, `minProperties`, schema-valued `additionalProperties`, `prefixItems`, `not`, `uniqueItems`, `allOf`/`if`/`then`, and many `format`s. The existing Node validator also omits some of these, e.g. `exclusiveMinimum` and schema-valued `additionalProperties` in `safety-config.schema.json:51-151`. Why it matters: a hand-rolled validator is not “~150 lines” unless it knowingly gives up contract semantics, and AC-027 would then mean “invalid under our subset,” not “invalid under the authoritative schema.” Recommended fix: either choose a real validator, or require a generated keyword inventory plus negative fixtures for every actual validation keyword before accepting C.

F2 - P1 - `docs/07-adr/ADR-0022-json-schema-validation-in-dotnet.md:75` and `tests/contract/validate_examples.mjs:71-124` - Cross-checking against the Node validator is insufficient evidence. The Node validator is itself a permissive subset and does not fail on unsupported keywords. Why it matters: two validators agreeing can still agree on the same blind spot, especially for keywords the Node path ignores. Recommended fix: cross-check against an independent full draft 2020-12 implementation, or make the Node validator strict first and add negative fixtures for its current omissions.

F3 - P1 - `docs/07-adr/ADR-0022-json-schema-validation-in-dotnet.md:60-65` - The hand-roll precedent is misapplied. OD-006’s FC04 reader resembled a bounded protocol sliver: one connection, one outstanding request, one function code, explicitly testable framing (`ADR-0020:198-202`). Runtime JSON Schema validation resembles the rejected Modbus server more: a growing, externally specified language with tricky applicator semantics and schema evolution risk. Why it matters: this looks like motivated reasoning caused by licensing discomfort with Option A. Recommended fix: remove the precedent claim, and compare C on its own cost/risk against full validators.

F4 - P1 - `docs/07-adr/ADR-0022-json-schema-validation-in-dotnet.md:57` and source: Corvus README - The ADR misses at least one serious .NET option: `Corvus.Text.Json.Validator` / generated schema evaluators. Corvus claims full draft 4 through 2020-12 validation and has a runtime validator package; NuGet shows Apache-2.0 for `Corvus.Json.Validator`. Source: https://github.com/corvus-dotnet/Corvus.JsonSchema and https://nugetprodusnc.azure-api.net/packages/Corvus.Json.Validator/4.5.3. Why it matters: the decision space is not exhausted, so recommending a custom validator is premature. Recommended fix: add Option E for Corvus, run the same measurement suite plus license scan, then decide.

F5 - P2 - `docs/07-adr/ADR-0022-json-schema-validation-in-dotnet.md:34-56` and source: NJsonSchema issue - The NJsonSchema `const` claim is accurate, but “disqualified” is too absolute. There is an open NJsonSchema bug showing `const` validation passes when it should fail: https://github.com/RicoSuter/njsonschema/issues/1857. Given this repo uses `const` in many places, plain NJsonSchema is not acceptable. But a defensible workaround could exist only if it is a schema preflight plus generic `const`/unsupported-keyword guard with full negative fixtures. Why it matters: if C is allowed, then “NJsonSchema plus strict gap checks” deserves equal treatment, though I would still not choose it over a full validator. Recommended fix: either document why that hybrid is worse than C, or include it as an option and reject it with evidence.

F6 - P2 - `docs/07-adr/ADR-0022-json-schema-validation-in-dotnet.md:41-48` and source: NuGet license page - The JsonSchema.Net license reading is mostly correct but needs sharper wording. NuGet 9.4.0’s license page is the OSMF agreement, and the cached `.nuspec` points to `OSMFEULA.txt`; the agreement applies to binary releases for revenue-generating users above US$10,000, but also says the fee is not a license fee and that MIT governs source/self-compiled binaries. Source: https://www.nuget.org/packages/JsonSchema.Net/9.4.0/License. Why it matters: it conflicts with TOOLCHAIN’s “no membership-gated licence anywhere in the graph” claim, but it is not copyleft and the portfolio is exempt if non-revenue. Recommended fix: call it a binary maintenance-fee agreement, not simply “not MIT,” and require TOOLCHAIN/license-scan updates if Option A is chosen.

F7 - P2 - `docs/07-adr/ADR-0022-json-schema-validation-in-dotnet.md:72-74` - “Unsupported keyword is an error” closes only one silent-gap class and creates a schema-versioning cost. A new legitimate keyword would break consumers at build/startup unless there is a documented schema compatibility process. Why it matters: schema evolution is mandatory-review territory; failing loudly is good, but without versioning rules it can turn compatible contract growth into consumer outage. Recommended fix: specify whether unsupported keywords fail CI, service startup, or record validation, and require schema-version migration guidance for adding keywords.

F8 - P2 - `docs/01-requirements/ACCEPTANCE_CRITERIA.md:48-54` and `docs/06-development/TEST_SPECIFICATIONS.md:289-301` - The four acceptance conditions for C are not enough for AC-027 to mean much. AC-027 proves DLQ behavior, not validator correctness; KAFKA-002 requires one invalid record and one valid record. Why it matters: a validator that catches only one fixture can satisfy the Kafka flow while still accepting other schema-invalid records. Recommended fix: add an AC-027 prerequisite suite: per-schema valid fixtures, per-keyword negative fixtures, schema keyword inventory enforcement, and evidence that the production validator is the one used by KAFKA-002.

VERDICT: REJECT - I disagree with recommendation C. I would add and evaluate Corvus as Option E first; if it fails, I would take Option A with explicit TOOLCHAIN/license amendments over hand-rolling.
